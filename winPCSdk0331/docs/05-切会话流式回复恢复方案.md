# 切会话流式回复恢复方案

## 背景

当前 `ai-chat-viewer` 在会话 A 正在流式回复时切到会话 B，再切回会话 A，会丢失切走前已经渲染出的流式片段，只继续显示切回后新收到的片段。

根因是 UI 切换会话时会清空当前 `messages` 和 `StreamAssembler`，切回后只通过 `getSessionMessageHistory` 拉取服务端历史。未完成的流式回复通常尚未落库，因此服务端历史里没有这部分内容。

## SDK 修复思路

`SkillSdk` 已经将 WebSocket 消息先写入 `MessageCacheStore.applyStream(message)`，再分发给 UI listener。`MessageCacheStore` 按 `welinkSessionId -> messageId` 隔离缓存，并支持聚合：

- `text.delta` / `thinking.delta`：追加同一 part 的内容。
- `text.done` / `thinking.done`：补全或覆盖 part 内容。
- `streaming`：使用完整 parts 快照恢复当前消息。
- `snapshot`：写入服务端消息快照。
- `tool.update` / `question` / `permission.ask` / `permission.reply` / `file`：更新结构化 part。

因此，即使 UI 当前切到会话 B，只要 SDK WebSocket 仍收到会话 A 的事件，会话 A 的流式回复仍会在 SDK 本地缓存里继续聚合。修复时让 `getSessionMessageHistory` 在首屏请求中合并当前会话的本地聚合消息，即可恢复尚未落库的流式片段。

合并规则：

- 未传 `beforeSeq` 时视为首屏请求，返回 `服务端 cursor history + 当前 session 本地最新聚合消息`。
- 传了 `beforeSeq` 时视为加载更早历史，保持服务端结果原样，避免重复插入当前流式消息。
- 服务端结果和本地聚合消息 id 相同时，以本地聚合版本参与本次返回，避免重复。
- `CursorResult` 的 `size`、`hasMore`、`nextBeforeSeq` 保持服务端返回。

## UI 兼容思路

SDK 能把旧片段重新带回 UI，但 UI 后续收到同 `messageId` 的 delta 时，`StreamAssembler` 可能仍是空状态。因此 UI 需要最小兼容：

- `StreamAssembler` 增加从 `MessagePart[]` hydrate 的方法。
- `App.tsx` 在处理同 `messageId` 的后续流式事件前，若 assembler 是新上下文，先从当前 `messagesRef` 中同 id 消息的 parts 恢复。
- 处理 `streaming` 事件时，也同步 hydrate assembler，保证后续普通 delta 接着已有内容拼。

## 缓存淘汰策略

为避免长期不调用 `closeSkill()` 时内存持续增长，`MessageCacheStore` 增加内部默认上限：

- `MAX_CACHED_SESSIONS = 50`：最多缓存 50 个会话，超过后淘汰最久未触达会话。
- `MAX_MESSAGES_PER_SESSION = 200`：单会话最多保留最近 200 条消息。
- `MAX_LOCAL_MESSAGES_PER_SESSION = 10`：单会话最多保留最近 10 条本地流式聚合消息。
- `MAX_FINAL_TEXTS_PER_SESSION = 100`：单会话最多保留最近 100 条最终文本。

淘汰时同步清理 `sessions`、`localSessions`、`finalTexts`、`orderedMessageIds`，保证同一消息在各缓存结构中一致。

## 验收

- 切会话后再切回，尚未落库的流式回复旧片段可以恢复。
- 切回后继续收到 delta 时，最终内容是旧片段加新片段，不丢失、不重复。
- 加载更早历史不会重复插入当前流式消息。
- 会话和消息缓存超过上限后按策略淘汰。
- `closeSkill()` 仍能全量清空缓存。
